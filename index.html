Case study · Delhivery B2C app · first-hand

I gave Delhivery 3 boxes. I got back 3 tracking numbers, and a live map that couldn't find my door.

Two problems, the fix I'd ship for each, and what it would return. About 3 minutes.

SCOPE Only the Delhivery B2C app, where individuals send parcels. These problems don't come up in the Delhivery business app or Delhivery One.
WHAT IT COSTS
₹7–13L / year

in one tier 2 city with 20 riders, lost to wrong-location detours and split deliveries. An outside-in estimate; the pilot narrows it.

Why it happens

Delhivery runs a quick-commerce live map on e-commerce addresses

Multi-day players skip live tracking and take text addresses. Quick commerce pins every drop. Delhivery sits in between, so it has to honour both.

If the live map stays, it has to run on a real pin.

How it works · the core

One service checks every pin once, at booking

The Address & Geofence Service reads top to bottom: first the registered pin code, then the user's live location. The result is stored on the order, and everything downstream just reads it. Pick a pin and follow its path.

What needs to be integrated

1

Google Maps SDK (Android + iOS)

THE PIN-DROP MAP
  • Draggable pin on the booking and receiver screens
  • Opens centred on the typed pin code
  • Same map tiles in the rider app
2

Pin-code boundaries

CHECK 1
  • One polygon per pin code, from Delhivery's own serviceability data
  • Server-side “point in polygon” test on every pin
  • Also draws the dashed boundary on the map
3

Device location permission

CHECK 2
  • Android Fused Location / iOS Core Location, “while using the app” only
  • Read once, when the user confirms the pin, with its accuracy
  • Never tracked in the background
4

Address & Geofence Service (new)

THE DECISION
  • Runs both checks and the 50m distance test
  • Writes lat/long + confidence onto the AWB
  • Threshold is a config value, tuned in the pilot
5

WhatsApp Business API

RECEIVER FALLBACK
  • Template message with a one-tap pin link
  • Reminder on day 2; order held after day 3
  • The receiver's pin goes through the same checks
6

Order, rider and tracking systems

READ ONLY, NO CHANGE
  • Order management stores the result
  • Rider app navigates to the pin and shows confidence
  • Customer live map shows the confirmed door
✕

Not used: geocoding the text address

DELIBERATELY LEFT OUT
  • Google can't always return coordinates for an Indian text address
  • The pin replaces the guess; the text stays for the rider to read
I CHOSEThe location pin is mandatory
OVERAn optional pin

The fix only works if nearly every order has a pin. An optional pin means low adoption.

I CHOSEFix the input, keep the live map
OVERHide the live pin when confidence is low

Hiding it is cheaper, but it hides the problem and gives up a differentiator.

I CHOSEThe sender pins; the receiver only as a fallback
OVERThe receiver always pins

It keeps booking in one flow. The receiver step runs only when the sender doesn't know the drop.

I CHOSEHold boxes by cause
OVERAlways ship together

A problem with one box's contents holds only that box. A network delay holds briefly, and communication comes first.

Where this still breaks, and my answer

6 edge cases I'd rather name than hide
BREAKS · UPSTREAMThe receiver never pins
MY ANSWERAfter 3 days the order is held. Some bookings may drop off; I'd measure it in the pilot.
BREAKS · UPSTREAMLocation permission denied
MY ANSWERCheck 2 can't run, so the user confirms by hand and the rider sees low confidence. Track the denial rate.
BREAKS · UPSTREAME-commerce brand shipments
MY ANSWERThe address comes from the brand's checkout, not our app. Out of scope for v1.
BREAKS · LINKED BOXESFailed attempt (NDR)
MY ANSWEREach box keeps its own status. The re-attempt goes to the validated pin, not the text address.
BREAKS · LINKED BOXESReturn to origin and damage claims
MY ANSWERRaised on the one affected box, but still visible under the parent shipment.
BREAKS · LINKED BOXESCash on delivery and SLA
MY ANSWERTracked per box, so billing doesn't change. The customer sees one combined status.

Measure

Four numbers tell me if it works. Each one drives the next.

1LEADING

Pin adoption

Bookings with a validated pin ÷ all bookings. Guardrail: drop-off at the pin step.

2LEADING

Pin accuracy

Pins accepted within 50m of the live location, or confirmed by the user ÷ all pins.

3LEADING

Rider detours

Deliveries with a call to the customer, or a stop outside the 50m geofence before the handover scan ÷ all deliveries.

4LAGGING

First-attempt success

AWBs delivered after a single out-for-delivery scan ÷ AWBs sent out. Pinned vs unpinned.

HOW I'D PROVE IT

A 4-week pilot in one tier 2 city, comparing pinned and unpinned orders. It wins if first-attempt success rises and drop-off at the pin step stays under 5%.
